# Decisions

Decision log for the AI homelab control plane. One entry per decision; newest at the bottom. A decision is changed by adding a new entry that supersedes it, never by editing history. Status: `proposed` (in an open PR), `accepted` (merged to `main`), `superseded by D-xxx`.

Reasoning lives in `reviews/ASTRA-V0-ARCHITECTURE-REVIEW.md` (cited as "review §n"). Keep entries short: context, decision, consequence, trigger to revisit.

---

## D-001 — Distribute jobs, not model tensors (V0)
- Status: accepted (PRINCIPLES.md §1, 2026-09-09); reaffirmed 2026-09-10 (review §9).
- Decision: no cross-machine tensor/pipeline parallelism over Wi-Fi/1 GbE between an Apple Silicon Mac and Intel laptops. Every model runs whole on one node.
- Revisit trigger: a single model the owner measurably needs that does not fit the largest single node, **and** an NVIDIA node exists with a ≥10 GbE link to a peer.

## D-002 — T7 filesystem: APFS (Encrypted), case-insensitive
- Status: proposed 2026-09-10 (review §10).
- Decision: format the T7 as APFS Encrypted, case-insensitive. Passphrase in the password manager. No exFAT, no case-sensitive APFS, no ext4.
- Consequence: Linux nodes can never mount the T7. All Linux access is via job payloads or read-only SMB from the Mac.
- Revisit trigger: the T7 must physically move between a Mac and a Linux box routinely (then a second, ext4-formatted drive is bought; the T7 is not reformatted).

## D-003 — The T7 is Mac-attached; the Mac is the storage host
- Status: proposed 2026-09-10 (review §10, §13).
- Decision: the T7 attaches to `mac-m4pro` over USB 3.2 Gen 2. Hashing, inventory, cataloging, and clonefile view generation run on the Mac. Linux workers do compute-heavy per-file jobs (transcode, transcription batch) on copies.
- Consequence: the Mac must stay awake/attached during ingest; `caffeinate` and a launchd job handle this. Internal disk must have ≥ 60 GB free (it had 12 GB on 2026-09-10).

## D-004 — Backup chain: T7 → append-only restic on dell-xeon → Backblaze B2
- Status: proposed 2026-09-10 (review §12).
- Decision: restic, rest-server `--append-only` on `dell-xeon`'s internal disk, nightly `restic copy` to B2 with a delete-less application key. Monthly restore drill. Consolidating onto the T7 is not a backup.
- Consequence: no source disk or SD card is wiped until the first successful restic snapshot **and** the B2 copy of that client folder both verify.

## D-005 — Node roster: retire dell-lite; dell-i7 reserved
- Status: proposed 2026-09-10 (review §14).
- Decision: `dell-lite` (8 GB, broken display) is retired. `dell-xeon` is the first and, for 60 days, only Linux worker. `dell-i7` is provisioned after the worker gate passes and is the designated candidate for a physically separate Kronos execution box.

## D-006 — Queue: SQLite behind a coordinator HTTP API; pull-based workers
- Status: proposed 2026-09-10 (review §15).
- Decision: one coordinator process (Python, on the Mac) owns `jobs.sqlite` and exposes claim/heartbeat/complete over HTTP on the Tailscale interface. Workers poll. Leases, attempts, idempotency keys, and JSON results are in the schema from day one. No Redis/NATS/RabbitMQ/Celery/Temporal/Ray/Nomad/Kubernetes.
- Revisit trigger (any one): >3 concurrent workers, >50k jobs/day, a second writer needed, or the coordinator must survive the Mac being closed — then the same API moves onto PostgreSQL on `dell-xeon`.

## D-007 — Network: Tailscale with ACL tags; no port forwarding
- Status: proposed 2026-09-10 (review §13).
- Decision: Tailscale personal plan; tags `tag:coordinator`, `tag:worker`, `tag:quant`, `tag:backup`; Tailscale SSH; ACL denies `tag:worker → tag:quant` and `tag:worker → tag:backup` entirely. Raw WireGuard rejected (key management for no benefit at this scale).

## D-008 — Inference runtime: Ollama on the Mac for V0; MLX/llama.cpp as measured alternatives; vLLM only on a future NVIDIA node
- Status: proposed 2026-09-10 (review §16).
- Decision: Ollama is the V0 model server (OpenAI-compatible API, fixed context per model, stable Metal). MLX is benchmarked side-by-side for the same model and adopted per-model only when it wins on measured tokens/s **and** passes a 24-hour stability run. CPU inference on Dells is limited to embeddings, whisper/parakeet transcription, and ≤4B classifiers; no CPU coding agents.
- Revisit trigger: an NVIDIA node arrives (vLLM there), or MLX server passes the stability run.

## D-009 — Catalog: SQLite on the T7 with sidecars as the durable, human-readable form
- Status: proposed 2026-09-10 (review §11, §19).
- Decision: `90-system/catalog.sqlite` (WAL, single writer = ingest daemon) is the query layer; per-asset JSON sidecars are the durable record and are regenerated from/into the catalog. Embeddings in `sqlite-vec` beside the catalog. Human corrections are a separate table that always wins over model output.
- Revisit trigger: >5 M assets, >3 volumes, or multi-writer need → PostgreSQL + pgvector on `dell-xeon`, same schema.

## D-010 — Coding agents run on Linux workers in disposable worktrees with per-repo, branch-scoped tokens
- Status: proposed 2026-09-10 (review §21, §22).
- Decision: no coding agent runs as the owner's primary macOS user. Agents run in sandboxed `systemd-run` units on `dell-xeon` with a fresh `git worktree`, a fine-grained GitHub token limited to that repository and to non-`main` branches, no access to `~/`, and network limited to GitHub and package registries. Frontier calls go through the router on the coordinator, never from the worker with a raw API key.

## D-011 — Kronos stays a separate trust domain: separate OS user now, separate machine before any live capital
- Status: proposed 2026-09-10 (review §24).
- Decision: Kronos research moves to a dedicated macOS user (`quant`) on the Mac immediately (separate keychain, home, HF cache). Broker/live credentials exist only inside that user's keychain / a separate password-manager vault. The general cluster may run Kronos **pure-function** jobs (public data in, files out) with no credentials. Before any live-capital gate exists, execution moves to a physically separate machine (`dell-i7` rebuilt, or a mini PC) tagged `tag:quant`, unreachable from `tag:worker`.

## D-012 — Metrics: every job writes a structured record to the catalog; no metrics stack in V0
- Status: proposed 2026-09-10 (review §25).
- Decision: `jobs` rows carry model, tokens, wall time, energy estimate, verification result, retries, escalation, and human-correction flags. A `report` CLI prints weekly summaries. Prometheus/Grafana/OTel are deferred until day 60+ and only if the CLI report is insufficient.

## D-013 — Video-derived artifacts are data, never instructions; candidate skills live outside `skills/`
- Status: proposed 2026-09-10 (review §20, §21; implemented in the same PR).
- Decision: `knowledge/` (ignored) holds all video-derived output including `knowledge/skill-candidates/`. Anything consumed by an agent from `knowledge/` is passed as delimited quoted data with an `untrusted` label. Promotion to `skills/` is a human PR.

## D-014 — Git governance: squash-only, auto-delete branches, GitHub Pro for rulesets, gitleaks + Dependabot in CI
- Status: proposed 2026-09-10 (review §32).
- Decision: repository settings become squash-only merges with branch auto-delete; `main` gets a ruleset (requires PR + `Python tests` + linear history, no force push, no deletion) — which requires GitHub Pro for a private repo; until then a local `pre-push` hook is installed. Dependabot for actions and pip; gitleaks in CI (secret scanning for private repos is a paid GitHub feature). CODEOWNERS and issue templates are not added.

## D-015 — Generated app repositories standardize on six files, not nine
- Status: proposed 2026-09-10 (review §22).
- Decision: `README.md`, `AGENTS.md`, `SPEC.md`, `ARCHITECTURE.md` (with an inline decisions section), `SECURITY.md`, `PLAN.md`. `TESTING.md` folds into `AGENTS.md` (commands) and `PROGRESS.md` is replaced by PR history plus `PLAN.md` checkboxes. A per-task **context pack** is generated by a tool, not hand-written.

## D-016 — Day-to-day ingestion is manual-first; AI never owns source deletion
- Status: accepted 2026-09-10 (owner direction).
- Decision: keep the one-time legacy dump non-destructive, but make recurring cleanup a separate transactional ingestion path. Desktop and Documents are manual-trigger only. Downloads is manual during development and may become opt-in automatic only after fault-injection acceptance tests pass and only for settled files. SD/removable media is detected automatically by volume UUID but a registered SD card still requires explicit apply before originals are removed.
- Safety boundary: crossing from Mac/SD to the T7 is implemented as copy-to-staging → close/flush → SHA-256 verify → atomic destination/register commit → source unlink. The LLM/VLM never receives permission to unlink source paths; it operates only after verified ingestion to classify, tag, name, and choose an organized destination. Unknown removable media and protected/excluded paths are never ingested automatically.
- Consequence: the owner gets a one-command / double-click cleanup flow without files disappearing while actively working. A later launchd watcher may automate Downloads, but mounting the T7 alone never empties Desktop or Documents.
- Relationship to D-004: this permits verified file-level moves during normal ingestion. Bulk wiping/reformatting of a source disk or SD card remains subject to the backup/restore policy in D-004.
- Revisit trigger: the manual triggers become meaningfully burdensome and telemetry/fault tests show the transactional path has operated safely for at least 30 days.

## D-017 — Keep the existing T7 as exFAT with Samsung hardware password protection
- Status: superseded by D-019 (2026-09-11; the owner exercised this entry's own revisit trigger and reformatted the T7 as APFS).
- Supersedes: D-002 in full and the `clonefile`/APFS-derived-view portion of D-003. D-003's Mac-attached storage-host role otherwise remains.
- Decision: do **not** reformat the populated Samsung T7. Keep its existing exFAT filesystem and use the T7's Samsung Magician password/security layer for at-rest protection. The owner unlocks the device before use; when locked/unmounted, ingestion must treat the T7 as unavailable and modify no source files.
- Consequences: exFAT provides broad portability but not APFS clonefile/snapshots or dependable POSIX ownership, ACL, symlink, hardlink, xattr, or filesystem-immutability semantics. Active Git workspaces remain on internal/native filesystems. The organized view uses catalog-backed paths or verified ordinary copies rather than hardlinks or `cp -c`. Legacy-dump integrity is enforced with hashes/manifests, transaction rules, backups, and application policy rather than `chflags`.
- Catalog consequence: the T7 remains Mac-attached and single-writer for ingestion. SQLite/sidecar state must be checkpointed/closed cleanly before planned disconnects, and the backup chain remains mandatory because exFAT has weaker crash-recovery semantics than APFS.
- Revisit trigger: the owner obtains another storage device or explicitly chooses a downtime/migration window where all T7 data is independently verified elsewhere and the benefits of APFS outweigh the migration cost.

## D-018 — Immediate V0 off-site backup: encrypted restic via rclone to Google Drive
- Status: accepted; operational since 2026-09-12. OAuth is configured, a snapshot, `backup-t7-check`, and a real `restore-t7-drill` all completed successfully on 2026-09-12, and both the nightly `com.ai-homelab.t7-backup` and weekly `com.ai-homelab.t7-check` LaunchAgents are loaded.
- Supersedes: the **immediate-target** portion of D-004 only. D-004's later independent `dell-xeon` append-only repository and Backblaze B2 copy remain desirable separate failure domains.
- Decision: while the Dell/B2 path is not yet provisioned, `angel` (the Samsung T7) is backed up to the dedicated repository `rclone:gdrive-backup:AI-Homelab-Backups/T7-restic`. Restic encrypts, snapshots, and deduplicates data before rclone stores repository objects in Drive. Google Drive Desktop mirroring/sync is not a backup mechanism.
- Consequence: Drive is off-site but is neither immutable nor append-only. The Mac's dedicated OAuth scope and Keychain-held restic password are still sensitive; a compromised Mac/Drive account could delete repository objects. This does not replace the future append-only Dell copy.
- Revisit trigger: the Dell append-only repository is operational and has passed a restore drill, or Drive retention/availability/cost no longer meets the requirement.

## D-019 — T7 `angel` reformatted as APFS (Encrypted); volume UUID is the identity of record
- Status: accepted 2026-09-12. Records a change the owner had already made physically: the volume was erased, recreated, and verified on `mac-m4pro`.
- Supersedes: D-017 in full. Reinstates the substance of D-002 (APFS Encrypted, case-insensitive) and restores the APFS-dependent portions of D-003.
- Trigger: D-017's revisit trigger contemplated a deliberate migration window with T7 data independently verified elsewhere. **That is not what happened.** The exFAT volume began returning I/O errors (31,769 read failures recorded in `~/Desktop/angel-recovery-logs/rclone-recovery.log` on 2026-09-11); two salvage attempts ran against a failing filesystem, each capturing a different partial subset, and the volume was then erased and recreated as APFS. The reformat was a response to failure, not a planned migration. See `docs/09-backup-recovery.md` for exactly what was and was not salvaged.
- Decision: `angel` is an APFS (Encrypted, FileVault-backed) volume mounted at `/Volumes/Angel`. At-rest protection is APFS encryption rather than the Samsung Magician password layer; the passphrase belongs in the password manager. Its macOS **Volume UUID is the authoritative identity** and is recorded once, in the gitignored `config/ingest.yaml` under `t7.volume_uuid`. No tracked file, doc, or script may hard-code it, and no code path may fall back to matching on the volume name `Angel` or the path `/Volumes/Angel`.
- Consequences: APFS restores native POSIX ownership/ACL/symlink/hardlink/xattr semantics, snapshots, and `clonefile`. The prohibitions D-017 placed on the derived view (no hardlinks, no `cp -c`) are **not** automatically lifted — the no-hardlink rule in `docs/02` stands on its own correctness grounds, and adopting clonefile for the organized view requires its own decision. Linux nodes cannot mount encrypted APFS at all (review §10), so all worker access stays job-payload or read-only SMB from the Mac.
- Consequence: the reformat issued a new Volume UUID. Every snapshot taken before 2026-09-11 is tagged with the retired UUID `3EE676ED-…` in `.state/backup-logs/`; that record is the provenance link back to the pre-erase data and must not be edited away.
- Open risk: a reformat does not repair failing hardware. This drive produced tens of thousands of read errors days ago. Do not treat it as trustworthy primary storage until it passes a full-capacity write-then-verify pass, and do not let it become the only copy of anything.
- Revisit trigger: the T7 must routinely mount on a Linux box (buy a second ext4 drive instead; do not reformat this one), or the owner replaces the device.

## D-020 — Naming is universal where useful; Angel retention is selective
- Status: accepted 2026-09-12 (implemented in `tools/ingest/naming/` and `tools/ingest/triage/`).
- Decision: naming and retention are separate decisions reached by separate code from separate evidence. Every eligible settled file is asked what it should be called; only some files are then asked whether they belong in the durable Angel library. A screenshot may be renamed and never archived.
- Decision: `IGNORE` means "not in the durable library". It never means "delete from the Mac", and no code in the naming or triage layer can delete anything. The only file removal in this system remains the source unlink inside `transaction.transfer_file`, after the bytes are verified on Angel.
- Decision: age in Downloads is a settle signal, not a value signal. A file being old enough to be safe to touch says nothing about whether it is worth keeping; the two are never conflated.
- Consequence: triage is biased toward `REVIEW`. A false `REVIEW` costs the owner a glance at a report; a false `INGEST` puts junk in a permanent library that restic then backs up forever.
- Consequence: the two answers are stored in different tables (`naming_history` and `classification_runs`), so a later change to one cannot silently rewrite the other.
- Revisit trigger: the review queue grows faster than the owner clears it for 30 consecutive days, which would mean the REVIEW bias has stopped being conservatism and started being an unread inbox.

## D-021 — The naming ledger lives on the Mac, not on Angel
- Status: accepted 2026-09-12 (implemented as `LocalLedger` in `tools/ingest/ledger.py`).
- Decision: a second SQLite database at `.state/file-intelligence/local-ledger.sqlite` holds naming and triage bookkeeping for files that have **not** been ingested: `local_files`, `naming_history`, `classification_runs`, `media_metadata`, `duplicate_observations`, and `runs`.
- Rationale: naming must keep working with Angel unplugged. Putting the naming ledger on the T7 would have quietly made every naming decision depend on the drive being connected, which contradicts D-020.
- Decision: durable truth about ingested assets stays in the T7 catalog (`90-system/catalog.sqlite`), which is what restic backs up. The two databases share table shapes via `schema_sql.py` so a file's record has the same form before and after ingestion.
- Consequence: the local ledger is rebuildable state, not truth. Losing it costs bookkeeping and at worst one redundant re-evaluation of a file's name; it never costs a file. It is therefore deliberately not backed up.
- Consequence: local file identity is `(device, inode)`, not path — a path-derived identity would make every rename look like a new file and lose both the audit lineage and the human-correction lock.
- Revisit trigger: a second machine needs to participate in naming, at which point one Mac-local ledger stops being sufficient and the identity scheme needs a host component.

## D-022 — A model proposes; trusted code disposes
- Status: accepted 2026-09-12 (enforced structurally by `tools/ingest/naming/`).
- Decision: the proposer boundary is enforced by the shape of the data, not by convention. A `NameProposer` receives `NamingEvidence`, which contains no `Path`, no file handle, and no callable — so it has nothing to mutate the filesystem with. It returns a string and a confidence.
- Decision: `naming.policy.safe_rename` is the only rename primitive. It cannot overwrite: it uses `os.link` + `unlink` (atomic, fails if the target exists) with an `O_CREAT|O_EXCL` reservation fallback where hardlinks are unavailable. `os.rename` is not used anywhere, because it silently clobbers on POSIX. It takes a *name*, not a path, so it cannot relocate a file either.
- Decision: the extension comes from the file, never from the proposal. `transaction.transfer_file` remains the only code in the system that unlinks a source.
- Decision: human corrections outrank all later model output, permanently. `organize correct-name` records an owner-authored name; from then on the automatic path refuses to reconsider that file regardless of what any future proposer suggests.
- Consequence: swapping the deterministic proposer for a model-backed one changes nothing downstream. The seam is a protocol; no safety property depends on which implementation is behind it.
- Revisit trigger: a proposer needs input the evidence record cannot carry as plain data — if that ever means handing a proposer a live handle, this decision must be reopened rather than quietly widened.

## D-023 — `00-inbox/organized` keeps its name; its semantics are documented instead
- Status: accepted 2026-09-12.
- Context: the directory name overstates what it holds, and a rename to `00-inbox/ingested/` was evaluated.
- Decision: keep the name for this phase. The path is referenced by `t7.inbox_relative_path` in the live `config/ingest.yaml`, by the code default in `tools/ingest/config.py`, by `config/ingest.example.yaml`, and by `tests/ingest/helpers.py`; the volume's live `00-inbox/` tree already carries the configured `restore_drill_relative_path`, which points at a real file that the restore drill verifies. Renaming would be silent path churn across config, code, tests, and an operational drill for an aesthetic gain.

## D-024 — Production automation is opt-in, hourly, and one-shot
- Status: accepted 2026-09-12 (`launchd/com.ai-homelab.file-intelligence.plist.template`, `scripts/file-intelligence-scheduled`).
- Decision: scheduling is launchd `StartCalendarInterval` at minute :20, not a resident FSEvents daemon. A one-shot invocation is inspectable, cannot leak memory or file descriptors, and a missed firing is recovered by the next one rather than needing supervision.
- Decision: disabled by default. `scripts/install-file-intelligence-launchd` parses `config/ingest.yaml` as YAML with the repository's own interpreter and refuses to install unless `automation.enabled` is literally `true` — a commented-out or unrelated nested `enabled: true` is not consent to schedule a process that reads and moves the owner's files.
- Decision: runs take a non-blocking `flock` in the state directory. A second run skips and exits cleanly rather than queuing; the next hourly firing picks the work up, and a backlog of blocked scans is worse than a missed one. The kernel releases the lock if the process dies, so a crash cannot wedge the pipeline.
- Decision: automated runs use `max(settle_seconds, downloads_watcher_min_settle_seconds)`. Taking the maximum rather than switching means lowering one value in config can never quietly shorten the window an unattended job waits.
- Consequence: enabling the agent does not enable transfers. `triage.auto_ingest` is a separate, independently defaulted-off gate, so the first thing the agent does once scheduled is name and report, not move.
- Consequence: the agent's only sources are Downloads and Screenshots. Desktop and Documents remain manual-trigger only (D-016), and scheduling this agent does not change that.
- Revisit trigger: the hourly cadence demonstrably misses files that matter (a same-hour download acted on before the next firing), or the run regularly exceeds an hour and the skip path becomes the normal path rather than the exception.

## D-025 — Screenshots are a configured source with no inferred default path
- Status: accepted 2026-09-12 (`sources.screenshots` in `config/ingest.example.yaml`; reported by `organize doctor`).
- Context: screenshots are the strongest case for automatic naming — macOS generates them with a timestamp name and nobody ever renames them by hand. macOS also writes them to `~/Desktop` by default, and `com.apple.screencapture location` can point at any directory.
- Decision: `sources.screenshots.path` has no default. It ships as `null` with `enabled: false`, and screenshots are a naming source only when the owner sets that path deliberately. The macOS setting is never read and adopted as the path.
- Rationale: inferring the path would, on a default Mac, silently enrol the entire Desktop in an hourly renaming pipeline. A convenience that widens the blast radius to a directory the owner never nominated is not a convenience. Screenshots are a *naming* source specifically — this decision says nothing about whether any screenshot is kept (D-020).
- Decision: `organize doctor` reports what `com.apple.screencapture location` currently says so the owner can copy it into config; it reports, it does not adopt. Where a configured screenshots path overlaps Desktop, Documents, or Downloads, only files whose names identify them as screen captures are evaluated.
- Consequence: on a machine that never configures it, screenshot naming simply does not happen. That is the intended failure mode, not a gap.
- Revisit trigger: macOS gains a capture location that cannot collide with a document folder, or the owner wants a dedicated screenshots folder picked up without configuration.

## D-026 — `t7.storage_root_override` requires an explicit CLI flag
- Status: accepted 2026-09-12 (`--allow-dev-storage-root`, enforced in `tools/ingest/t7.py`).
- Context: `t7.storage_root_override` exists so tests and local dry runs can point the pipeline at a scratch directory. As originally written it was honoured from config alone, and honouring it skipped the volume-UUID check for the **entire** destructive path — including the source unlink. A stale override left in `config/ingest.yaml` would have let `--apply` verify a copy into an ordinary folder and then delete the owner's original.
- Decision: the override is honoured only when `--allow-dev-storage-root` is passed on the command line for that invocation. A config file alone can never disable the UUID boundary. The scheduled LaunchAgent never passes the flag.
- Relationship to D-019: the D-019 boundary is unchanged and absolute. The T7 is identified by its Volume UUID, recorded once in the gitignored `config/ingest.yaml`, and no code path may fall back to the volume name `Angel` or the path `/Volumes/Angel`. This entry carves no exception into that rule; it closes a path that had quietly bypassed it.
- Consequence: `organize doctor` reports a configured override as a finding and states that it is honoured only with the flag, so a development setting cannot sit unnoticed on a production machine.
- Revisit trigger: the test suite builds its configuration in-process and no longer needs the override at all, at which point it should be deleted rather than gated.


## D-027 — Content identifies bytes; asset rows identify source occurrences
- Status: accepted 2026-09-12.
- Context: Phase 1A derived `asset_id` from `(source_volume_id, original_path)` and enforced `UNIQUE(source_volume_id, original_path)`. That made retries simple, but a normal event — deleting `Downloads/invoice.pdf` and later downloading a different `invoice.pdf` — forced two unrelated files into one identity. The safety patch in PR #9 correctly refused the collision, but could only park the second file in `needs_review`.
- Decision: a pathname is provenance, not identity. `blobs.sha256` is the content identity. Each `assets` row is one source occurrence and new IDs are derived from `(source volume, original path, verified SHA-256)`. The catalog may therefore contain multiple rows for the same source path when different bytes occupied it over time.
- Decision: byte-identical files at different paths remain distinct asset/provenance rows that reference the same blob. Recognizing equality never authorizes duplicate deletion or garbage collection.
- Decision: the transfer hashes and re-stats the source before selecting an asset row. Resume lookup by path is permitted only when the source is absent and there are no bytes available to hash; that path may finish bookkeeping but can never authorize deletion of a newly present file.
- Decision: immediately before the only source unlink, the pipeline re-verifies both sides: the destination still hashes to the recorded content and the source still has the same device/inode/size/mtime fingerprint and SHA-256 that were copied.
- Migration: catalog migration 4 atomically rebuilds `assets` to remove the legacy `UNIQUE(source_volume_id, original_path)` constraint while preserving all existing asset IDs and rows. Existing IDs are not rewritten; new IDs use the content-aware scheme.
- Consequence: a path can be reused safely, exact duplicates remain auditable as separate occurrences, and an in-place rewrite or pathname swap during ingestion cannot inherit the prior file's deletion authority.
- Revisit trigger: the catalog later needs a first-class source-occurrence table separate from `assets` for multi-location lifecycle tracking; if so, migrate provenance there without changing `blobs.sha256` as content identity.

## D-028 — Different bytes never inherit content-specific authority
- Status: accepted 2026-09-12.
- Context: the Mac-side local identity is based on `(volume, device, inode)` so it survives a rename. An inode can also be reused, and applications can rewrite an existing inode in place. Those two cases cannot be distinguished reliably after the bytes have changed.
- Decision: once a previously observed local identity has a different SHA-256, it starts a new ledger generation even when the inode and pathname are unchanged. Earlier naming/classification rows remain as audit history but are out of scope for the new bytes.
- Decision: retention, classification, model naming judgments, and ingestion linkage are content-specific and never cross a generation boundary automatically.
- Decision: explicit human naming authority is different. When changed bytes remain at the same path on the same local identity, the owner's filename lock is re-asserted into the new generation because invariant 12 says a person's name outranks later automation. If the inode is reused at a different path, no naming authority carries forward.
- Decision: a generation reset has no filesystem authority. It never renames or deletes the path by itself.
- Decision: the hourly hash cache requires unchanged path, size, mtime, and ctime. Angel refreshes the observation timestamp after its own rename so rename-generated ctime does not force a redundant re-hash; a later content rewrite still advances ctime and invalidates the cache even if mtime is restored.
- Consequence: rewritten bytes cannot inherit stale retention/deletion authority, inode reuse cannot inherit a stranger's lineage, and ordinary edits do not revoke an owner-authored filename.
- Revisit trigger: a stronger platform file-generation identifier becomes available and is proven stable across renames but changes on replacement, allowing edits and replacements to be distinguished without trusting path or timestamps.

## D-029 — Perception is built before it is trusted; evidence has no authority in this phase
- Status: accepted 2026-09-12.
- Context: naming a screenshot meaningfully requires reading what it shows, which needs OCR and image understanding. The obvious move is to build perception and immediately feed it to the namer. The obvious move is wrong: a perception layer's failure modes are only discoverable by running it over real files, and wiring it into decisions on day one means discovering them by way of misnamed or misfiled documents.
- Decision: `tools/ingest/evidence/` implements FACTS only. It collects native text, OCR blocks with geometry and confidence, a vision description, and layout structure, caches them, and exposes them for inspection. It changes no naming, retention, or ingestion decision.
- Decision: the separation is structural, not a convention. No module under `tools/ingest/naming/` or `tools/ingest/triage/` may import anything from `tools/ingest/evidence/`, and a test walks their ASTs and fails the build if one does. The perception call in `pipeline.py` sits deliberately *below* both decisions, which are already final by the time it runs.
- Decision: OCR and vision are separate seams (`OCRBackend`, `VisionBackend`), never one "understand this file" interface. "What text is visibly present" and "what am I looking at" are different questions with different engines and different failure modes.
- Decision: model-facing backends receive `RasterImage` PNG bytes, never a `Path`. A backend that may one day be a model is not trusted and then constrained; it is not given the means. Trusted in-repo `TextExtractor` implementations do receive a path, because they must stream large files, and because they are deterministic repo code rather than inference.
- Consequence: the evidence corpus accumulates from the hourly run, can be inspected with `organize evidence`, and can be characterized before anything is allowed to act on it. The interpretation layer (evidence to likely client/project/category) is a separate future stage, not a fold into the namer.
- Revisit trigger: a real OCR and vision backend have run over the owner's actual Downloads and screenshots for long enough to characterize their failure modes, and a separate, testable interpretation stage exists with its own confidence. Then, and only then, evidence becomes an input to a proposal — still a proposal, still validated, still outranked by a human's name.

## D-030 — Extracted document text stays on the Mac and out of normal output
- Status: accepted 2026-09-12.
- Context: `media/probe.py` deliberately records only `text_available: bool` for PDFs and drops the extracted text, because the T7 catalog is restic-backed to Google Drive and would otherwise become a searchable, off-site copy of every contract, medical letter and tax return on the disk. The evidence layer has to store text to be useful at all, which reopens exactly that question.
- Decision: evidence is stored only in the Mac-side local ledger (mode 0600, not backed up by restic, rebuildable). The `file_evidence` table is deliberately absent from the T7 catalog's migration chain entirely — not merely unwritten there, so there is no table for a future accident to write into.
- Decision: stored text is bounded (`evidence.max_text_chars`, default 20 000, with a `truncated` warning). It is evidence about a document, not a mirror of one.
- Decision: `media_metadata.facts` is unchanged and gains no text. Measured facts and perceived content stay in separate tables.
- Decision: `organize evidence` prints no extracted text by default — route, producers, versions, confidences, counts and warnings only. `--show-text` is an explicit per-invocation act. Nothing writes extracted text to a log file, because an `organize` run piped to a log would otherwise persist it.

- Revisit trigger: evidence needs to survive on Angel for assets that have been ingested. If so, decide separately and explicitly what may cross to a restic-backed volume — plausibly structure, confidences and image kinds, but not verbatim document text.

## D-031 — Perceived evidence is cached by content, never by pathname
- Status: accepted 2026-09-12.
- Context: OCR and vision are expensive, so results must be cached; and D-027/D-028 already established that a pathname is an observation rather than an identity. A perception cache keyed by path would reintroduce exactly the bug those decisions removed, one layer out, with the failure mode "this scanned contract inherited the OCR text of the different file that used to have this name".
- Decision: the cache key is `uuid5` over the content SHA-256, the evidence kind, the producer and its version, the model and its version, and the evidence pipeline version. A pathname appears nowhere in it. A rename with identical bytes therefore reuses the work; different bytes at the same path cannot find a row to inherit.
- Decision: a backend or model version bump invalidates only the evidence kind it can have changed. Upgrading the OCR engine misses the OCR rows and leaves native-text and vision rows valid.
- Decision: the pipeline version folds in a digest of the configuration that changes *what a producer sees* (raster DPI, page cap, pixel budget, text cap, block cap), so lowering the raster DPI invalidates the OCR taken at the old one automatically. Timeouts and `enabled` flags are excluded: they decide whether a stage runs, not what it would perceive.
- Decision: a backend reporting itself unavailable is recorded as a warning but is **not** cached. Availability is a property of the machine, not of the bytes; caching absence would mean installing an OCR engine never re-asks about anything already scanned.
- Decision: `file_evidence` upserts rather than appending. That is not a violation of the append-only rule governing `naming_history` and `classification_runs`: the key already encodes every input that could make the answer different, so a second write under the same id is a re-derivation of the same question, not a competing judgment.
- Consequence: the hourly run is cheap on a folder that has not changed, a rename costs nothing, and stale perception cannot be attributed to bytes it never described.
- Revisit trigger: evidence becomes an input to a decision (see D-029), at which point a cache hit is load-bearing for that decision and the key may need to include the interpretation layer's version as well.

## D-041 — Prompts are versioned first-class configuration, rendered identically for evaluation and production
- Status: accepted 2026-09-12 (architecture direction; registry not yet implemented — see `docs/20-prompt-management.md`).
- Context: today's only model-facing prompts in the evaluation path are three unversioned literal templates in `tools/bench/harness.py:benchmark_prompt()`. There is no prompt identifier, no schema, and no recorded link between an evaluated prompt and whatever a production caller would eventually send.
- Decision: a prompt is addressed by `prompt_id` + `version`, never by an unversioned string. Composition is layered and reasoned about separately: policy (trusted), role, task contract, context pack (untrusted data — D-022/D-028/D-029/D-036 apply unchanged), tool contract, output contract, few-shot examples, and a runtime adapter that converts to a specific provider's wire format. Production inputs differ from evaluation inputs; the prompt recipe does not. Production performance belongs to `model × runtime × prompt × role`, not the model alone.

## D-044 — Angel does not certify models on raw standalone intelligence; certification requires a production-capability benchmark
- Status: accepted 2026-09-12 (architecture direction; the distinction below applies to future evaluation, not a re-scoring of past results).
- Context: a bare model given a generic instruction and a model given a full production task contract are different, measurably different-performing configurations. Treating the first as evidence for the second overstates what a cheap/small model can do in production and understates what it can do when properly augmented.
- Decision: Angel's production execution unit is `model + task-specific production prompt + bounded spec/context + relevant trusted skills/capabilities + approved libraries/reference material + tools + a deterministic verifier` — not the model alone. Small/local models are intentionally meant to be capability-augmented this way; the research question for SLMs (D-039) is what is the smallest model that reliably passes the real production contract for a given task class, with this full augmentation present.
- Decision: a **raw-model baseline** (bare instruction, no production prompt/spec/skills/tools) is diagnostic information only and is never routing or certification evidence. A **production-capability benchmark** (the full execution unit above) is the only evidence that may support a certification record (D-042) or a Gate 2 claim (`PLAN.md` Phase 2). The two are never reported as one number.
- Decision: the historical Legacy 20 results (D-040) are raw-model-baseline-shaped — one generic contract per task kind, uniformly applied, with no task-specific spec or skill augmentation. They remain valid historical/regression evidence under that label and are not reinterpreted as production-capability results by this decision.
- Consequence: production task classes are evaluated with the same skills/spec/reference material a production job of that class would actually receive (task-driven selection, never the entire skill library injected by default), per `docs/19-model-evaluation.md` §8–§10 and `docs/20-prompt-management.md` §2. An augmentation ablation experiment (raw instruction → production prompt → +spec → +skills → +skills+reference/tools) is designed in `docs/19-model-evaluation.md` §10 to measure augmentation's marginal value, scheduled to run after the D-038 trusted fixture runner exists, not before.
- Revisit trigger: the ablation experiment runs and its results either confirm or revise how much augmentation later SLM-by-role benchmarking (`PLAN.md` Phase 2) uses by default.

## D-047 — D-045 superseded: the fixture verdict moves outside the process it judges
- Status: accepted 2026-09-14 (`tools/fixtures/probes.py`, `tools/fixtures/runner.py`, `tools/fixtures/_probe_driver.py`, `tools/fixtures/sandbox.py`, `tests/test_fixture_runner.py`).
- Context: D-045 claimed the runner "returns real PASS/FAIL evidence" and that "a model's own success claim is never read for the verdict". The first half was false. The runner executed verifier-owned `unittest` files **in the same process that imported the candidate's `solution.py`** and read the process exit code as the verdict. Candidate code runs first, at import, and controls that process. Two one-line submissions demonstrated it against the real `code-01` bundle: `import os; os._exit(0)` with `add` returning `0` exited before a single assertion ran and scored `status="passed"`; rebinding `unittest.TestCase.assertEqual` to a no-op made all four assertions vacuous with `add` returning the string `'nope'`, and also scored `passed`. The existing tamper check compared only on-disk SHA-256 of the hidden test files, so in-memory subversion was invisible. This is D-038's defect one layer down: the verdict channel moved from a JSON field the model writes to an exit code the model controls. D-045's own revisit trigger ("a demonstrated fixture or isolation defect") is what fired.
- Decision: **no verifier-owned comparison logic runs inside the sandbox.** A fixture is now a set of *probes* (`tools/fixtures/probes.py`). Each probe is split across the trust boundary: a `source` fragment runs inside the sandbox, imports the candidate, performs one bounded interaction, and assigns `OBSERVED`; the `expected` value stays in the parent process and is never written into the disposable directory, the probe source, `argv`, or the environment. Each probe runs in its own short-lived sandboxed process spawned by the trusted parent, so a candidate cannot read ahead to probes it has not been given. Manifest version 2 replaces `hidden_test_files`/`run_module` with `probes`; version 1 bundles are refused, not reinterpreted. `hidden/` directories are deleted rather than orphaned.
- Decision: **absence of an observation is a failure.** A submission that exits, hangs, crashes, or suppresses the driver produces no observation line, and the runner scores `no-observation`. Fail-closed is now a property of the construction rather than of a check someone remembered to write. The whole fixture passes only when every probe was observed *and* matched; an empty probe set is a `verifier-error`, never a vacuous pass.
- Decision: **probe inputs are randomised from a recorded seed.** A memorised answer table keyed on fixed inputs does not survive a second run; the seed is recorded on the result so a failure is still replayable exactly.
- Decision: the sandbox profile now **denies reads under the invoking user's real home directory**, re-allowing only the interpreter's own install prefixes. D-045 documented a read-confidentiality gap as reachable by "a candidate that already knows (or successfully brute-forces) an absolute path"; in fact `pwd.getpwuid(os.getuid()).pw_dir` returns the real home regardless of `HOME`, and a probe enumerated the owner's home directory and read `~/.ssh`. The `HOME` redirect is a convenience, not a boundary, and `tools/fixtures/sandbox.py` now says so. The remaining gap -- world-readable system paths outside `~` -- is unchanged and still documented, because a tight allowlist crashes `dyld`.
- Consequence, stated rather than hidden: **the code fixtures' semantics changed**, so D-046's code-task numbers are not directly comparable to future runs. `code-01` and `code-03` (the two that passed) keep their contracts and gain randomised inputs. `code-04` gains a probe for `summarize` still behaving as before -- `task.md` always said "Do not change `summarize` itself" and nothing verified it, which is the exact failure D-046 observed and could not see. The Legacy 20 corpus, its answers, and `docs/18-phase-2-evaluation.md` are untouched, and tests enforce that.
- Consequence: the residual limit is the ordinary one for black-box testing, and is now the *only* one: inside its own process a candidate can print a forged observation for the single input it was given, but to be accepted that forgery must equal the correct answer for that input. Randomised inputs are what keep "compute the answer" from collapsing into "recall the answer".
- Revisit trigger: a demonstrated way to obtain a PASS without producing correct observations; or a decision to run fixtures anywhere other than this macOS host, which still needs container/VM isolation before the remaining system-path read gap is acceptable.

## D-048 — "Nobody checked" is not "verified"
- Status: accepted 2026-09-14 (`tools/router/router.py`, `tools/router/report.py`, `tools/coordinator/ledger.py`, `tests/test_autonomous_routing.py`).
- Context: `Router.route()` computed `verified = bool(request.verifier(output)) if request.verifier else True`, and `_record` then wrote `verifier_result="passed"` for that attempt. A job routed to a small local model with **no verifier at all**, returning the string `TOTAL NONSENSE, not an answer`, was recorded as `status='succeeded'`, `verifier_result='passed'`, and reported a `deterministic_verification_success_rate` of 1.0. This is the same failure as D-038 and D-047 at the telemetry layer, in the one append-only store that model certification (D-042) and the Phase 6 hardware decision (`PRINCIPLES.md` §12) both read.
- Decision: verification has three states, not two. `verified` means a deterministic verifier ran and passed; `verification_failed` means it ran and rejected; `completed_unverified` means none ran. The ledger stores `verifier_result = NULL` for the third, and `Attempt.verifier_ran` records it explicitly. A job that completed without a verifier gets disposition `unverified`, distinct from `success`.
- Decision: `tools/report` reports `verified_success_rate` (claims correctness) and `completion_rate` (claims only that output arrived) as separate numbers that are never merged, plus `verification_coverage` and `unverified_attempts`. Rates are computed only over attempts a verifier actually judged, so an unmeasured task class shows coverage 0 rather than a perfect score. `quality_by_task_class` gives Gate 2's "reporting surfaces capability-specific quality" clause something real to point at.
- Decision: `report()` treats a missing parent directory as an empty history. `python -m tools.report` -- the command `PLAN.md` has marked done since 2026-09-12 -- previously raised `sqlite3.OperationalError: unable to open database file` on any machine that had never routed a job, which is every machine including this one. The existing test used an *existing* temporary directory with a missing file, which is why it never caught it.
- Consequence: dispositions recorded before this date cannot distinguish verified from unverified. They are left as they are; the history is small and rewriting telemetry to make it look better is the opposite of the point.

## D-051 — Attended-autonomous routing: authorization, certification, and the task-class join
- Status: accepted 2026-09-14 (`tools/models/task_classes.py`, `tools/models/certification.py`, `tools/router/router.py`, `config/certifications.example.yaml`, `tests/test_autonomous_routing.py`).
- Context: the target workflow is *attended autonomous* -- a human present and able to stop the run, but not asked to approve each routing decision. The router could not support that. `RouteRequest.task_class` was recorded in the ledger and consulted by nothing; `RouteRequest.risk` was recorded and enforced nowhere; the registry aliased capability `code` to `text_generation`, so "this job needs code" was satisfied by any text model; and there was no certification concept at all, so selection was tier + declared capability + context length, which is parameter-count reasoning wearing a registry's clothes. Three vocabularies (`docs/19` §8 task classes, §2.1 suites, and the registry's capabilities) had no join between them.
- Decision: three gates, in order, each failing closed and each producing a named ledger event. **Authorization** — work above `autonomous_risk_ceiling` does not run without an explicit human authorization token, checked before candidate selection so no provider is contacted; an unrecognised risk label sorts above every known one, so a typo escalates to a human rather than downgrading to low. **Privacy** — confidential or local-only work never reaches a frontier provider, and a refused frontier is recorded with the rule that refused it rather than silently dropped. **Certification** — for a task class an ACB-v1 suite gates, only a configuration with a live, matching, measured certification is a candidate.
- Decision: `tools/models/task_classes.py` is the join, as versioned code rather than configuration: task class → required capabilities → gating ACB-v1 suite. An unknown task class is refused, never defaulted to `general`, because a typo would otherwise silently drop a certification requirement. A class either has a gating suite and requires certification, or has neither; a test enforces the biconditional. The three certifiable classes today are exactly Gate 2's minimum: `classification`, `routing`, `naming.semantic` (D-044).
- Decision: `code_generation` is a real registry capability. Certification, not declaration, is what makes it eligibility.
- Decision: a certification pins `runtime`, `quantization`, `prompt_version`, and `tool_schema_version`, and the router refuses when any of them differs from what it is about to run. **An unpinned prompt version therefore cannot satisfy any certification.** This is deliberate: it makes D-041's prompt registry a hard prerequisite for certified autonomous routing rather than a documentation aspiration, and it is the mechanical form of `docs/20` §4's "a prompt change is a capability change". Certifications also expire, and an absent certification file is refused rather than read as "nothing is required".
- Decision: `config/certifications.example.yaml` ships an **empty** list, and a test asserts it stays empty until a suite exists. That is Gate 2 being RED expressed as behaviour instead of as a sentence in a document: today, routing a certification-gated class escalates.
- Decision: `tests/test_autonomous_routing.py` is the readiness matrix, exhaustive over its axes rather than sampled, and it is platform-independent by construction (a test enforces that it contains no `skipUnless`), because routing policy is pure logic and must run on the CI host that gates merges. It also extends the Phase 1B AST mutation guard to `tools/{router,models,coordinator,bench,fixtures}` with the same explicit deletion-justification register the ingest layer uses.
- Explicitly not decided here: that any model may now be routed autonomously. Nothing is certified, so nothing gated can run. What this decision buys is that when a certification does exist, the gates it has to pass are enforced code with an exhaustive test matrix, rather than intentions.
- Revisit trigger: the first real ACB-v1 certification; or a second coordinator, at which point the authorization token needs an identity rather than only a presence check.

This Lab does not turn Gate 2 green, does not certify a model, and its development seeds may never be presented as validation or frozen-holdout evidence -- a fresh validation corpus is required before any such claim, per `docs/23-naming-lab.md`.
- Revisit trigger: a Lab-validated vNext prompt/grammar is ready to graduate -- at that point the deferred Gate-2 defects (this entry's third decision) should be fixed in `tools/bench/acb_v1/semantic_naming.py` and `tools/ingest/naming/policy.py`'s grammar reconsidered, as one dedicated, carefully-reviewed pass, not as a side effect of Lab development.

## D-055 — Video gets one sampled frame through the same vision backend as images
- Status: accepted 2026-09-17.
- Context: `router.py` shipped with `MEDIA_VIDEO` grouped into `_OPAQUE_MEDIA_KINDS` ("audio/video get no evidence backend in this phase"), so a `.mp4` reviewed in the Naming Lab (D-054) carried nothing but ffprobe container facts -- no sense of what the video actually shows, unlike every image, which already gets a vision-backend description.
- Decision: `tools/ingest/evidence/backends/ffmpeg_video.py` is a new module, added alongside `backends/tesseract.py` as the second (and, per the AST guard in `tests/ingest/test_mutation_authority.py::EVIDENCE_SUBPROCESS_JUSTIFICATIONS`, only other) module in the evidence package permitted to use `subprocess`. It samples exactly one representative frame (the midpoint of `duration_seconds`, or 1s if duration is unknown -- a video's first frame is disproportionately likely to be a fade-in/title card) via a fixed, no-shell `ffmpeg` argv, downscaled by ffmpeg's own `-vf scale=...` filter to at most 1280px on the long edge, read back as PNG bytes on stdout. No temp file is ever written -- no `-y`, no output path -- preserving the evidence package's "zero filesystem mutations" invariant (`tests/ingest/test_mutation_authority.py::EvidenceLayerNeverWritesTests`), the same way `tesseract.py` preserves it by reading TSV off tesseract's stdout.
- Decision: `router.py` removes `MEDIA_VIDEO` from `_OPAQUE_MEDIA_KINDS` and adds rule `r14-video-frame`: video routes to vision only, never OCR (a sampled frame is evidence of subject, not a text-bearing document; burned-in text such as a title card is left for a future dedicated rule rather than defaulted to OCR on every video). `extract.py::_raster_for_vision` now accepts `facts` (for `duration_seconds`) and dispatches to `ffmpeg_video.extract_frame` for `MEDIA_VIDEO`, reusing the exact same `_vision_stage`/cache-key/normalization path an image already goes through -- no parallel vision pipeline.
- Decision: audio remains opaque (no speech-to-text ships; out of scope of this change). A machine without `ffmpeg` on `PATH` degrades to a `backend_unavailable` warning, exactly like a machine without `tesseract`.
- Consequence: any caller of `collect_evidence` -- today, only the Naming Lab -- gets a real vision-backend description of a video's sampled frame for free, gated by the same `evidence.vision.enabled`/`backend` config every other vision call already respects (`null` by default in a from-scratch config; the Lab's sidebar already exposed `heuristic`/`ollama` choices before this change). `tools/naming_lab/preview.py::video_frame_preview_png` shows a reviewer the identical sampled frame the vision backend was handed, and `tools/naming_lab/runner.py::build_task_text` now includes `visual_description`/`visual_entities`/`visual_context` in the naming prompt's evidence text for any file with a vision result -- previously gathered but never surfaced to the model or the reviewer for any media kind.
- Revisit trigger: multi-frame sampling (start/middle/end, or scene-change detection) turns out to matter for videos where one frame is unrepresentative -- that is a `FileEvidence.visual` schema change (currently one `VisualEvidence`, not a tuple) and deserves its own review rather than an incremental patch here.

## D-056 — Multiple sampled frames, a configurable count, and OCR as a vision fallback
- Status: accepted 2026-09-17.
- Context: D-055 shipped one sampled frame per video, with its own revisit trigger anticipating exactly this: a video whose subject only appears partway through gets named from whatever one moment the midpoint happened to land on, and OCR (deliberately, at the time) never ran on a frame at all -- a vision model that reads on-screen text poorly, or not at all, had no fallback the way `r6-screenshot` already gives a screenshot image.
- Decision: `FileEvidence.visual` becomes `visual` (unchanged, now always the *first* sampled frame's description, for backward compatibility) plus a new `visual_frames: tuple[VisualEvidence, ...]` -- one entry per frame the vision backend was actually shown, length 1 for a photo/screenshot (always, structurally, since `_rasterize` returns a single-element list for `MEDIA_IMAGE`), length `video_frame_count` for a video. `ffmpeg_video.extract_frame` (singular, D-055, still used for a quick preview thumbnail) gains a sibling `extract_frames`, sampling `count` timestamps evenly spaced strictly inside the video's duration (never the exact start, likely a fade-in/title card; never the exact end, which may be past a container's last decodable frame).
- Decision: `router.py`'s `r14-video-frame` rule now sets `ocr = True` alongside `vision = True`. `extract.py::_rasterize` (previously OCR-only, used for a multi-page PDF or the one image) gains the `MEDIA_VIDEO` branch instead of the now-removed `_raster_for_vision`, and is called by *both* `_ocr_stage` and `_vision_stage` -- one `ffmpeg` run per frame, not two, and both stages see identical frames. `_ocr_stage`'s existing per-page loop (already written to handle "however many pages `_rasterize` returned," from the multi-page-PDF case) required zero changes to also OCR every sampled video frame; `_vision_stage` gained an equivalent per-image loop, mirroring `_ocr_stage`'s own partial-failure-does-not-abort-the-rest posture.
- Decision: `evidence.vision.video_frame_count` (`tools/ingest/config.py::VisionConfig`, default 5, valid range 1-30) is the configurable ROI knob the frame count is not hard-coded to -- folded into `pipeline_version_for` so changing it correctly busts cached vision/OCR evidence. The Naming Lab's sidebar exposes it as a live "Video frames to sample" control (`tools/naming_lab/app.py`), re-sampling and re-describing the current file immediately on change; `preview.py::video_frames_preview_png` shows the reviewer the exact frames the backends saw as a small gallery (re-sampled for display, since `FileEvidence` itself retains no raw pixel bytes -- by design, per the evidence layer's own minimal-retention posture).
- Consequence: a video's naming evidence (and, for the Lab, its Review-screen display and the naming prompt's task text) now spans several moments across the clip rather than one, and carries OCR text from every sampled frame the same way a scanned PDF's pages already do -- fixing both gaps D-055 flagged as future work, without introducing a second OCR/vision pipeline for video (both stages share `_rasterize`).
- Revisit trigger: evenly-spaced-by-time sampling proves a poor fit for a corpus with long static intros/outros -- scene-change-aware frame selection is a bigger, separate change (needs its own frame-difference heuristic or a second `ffprobe`/`ffmpeg` pass) and should not be folded into this decision's scope after the fact.

## D-057 — Evidence reaches naming through a plain-data bridge; the semantic proposer is opt-in and policy-gated
- Status: accepted 2026-09-17.
- Context: D-029 built a perception layer (native text, OCR, vision descriptions; later video frames, D-055/D-056) and deliberately wired it to nothing -- `docs/17-file-evidence.md`'s "What comes next" named three preconditions before evidence could influence any decision. All three are now met: real OCR and a real vision backend have run over a real corpus and their failure modes are characterized (the 2026-09-12 Phase 1C acceptance run, then D-054's interactive Naming Lab loop over real files); the interpretation layer exists as a separate stage (D-036); and the naming gate's ordering in `docs/16` is unchanged and still validates every proposal. Meanwhile production naming still proposed `2026-09-12_photo-4032x3024.jpg` for a file whose own text layer said what it was, and D-051's `naming.semantic` prompt was "still never exercised by a production caller."
- Decision: perceived evidence is granted authority over exactly **one** decision -- the filename -- and over nothing else. That is the smallest decision available and the one whose wrong answer costs a confusing name (correctable with `organize correct-name`) rather than a file. Retention triage stays evidence-blind: `tools/ingest/triage/policy.py` reads none of it, still may not import `tools.ingest.evidence`, and `pipeline.py` hands it a `NamingEvidence` with `perceived` *stripped off* rather than merely unread -- so a future change wanting retention to read OCR text must widen that call visibly instead of finding the field already there. Ingestion and automation read nothing produced by the evidence layer.
- Decision: the crossing is one reviewed module **outside** both guarded packages: `tools/ingest/perception_bridge.py`, structurally equivalent to `tools/naming_lab/evidence_bridge.py`'s position under D-054. The AST guard in `tests/ingest/test_evidence_security.py` forbidding any module under `tools/ingest/naming/` or `tools/ingest/triage/` from importing `tools.ingest.evidence` is therefore **unchanged and unrelaxed**, and a second guard (`PerceptionBridgeIsTheOnlyCrossingTests`) asserts the bridge plus the orchestrator that calls it are the only modules in `tools/ingest/` importing both sides, with a written justification per entry in the style of `DELETION_JUSTIFICATIONS`. The bridge imports only `evidence/types.py` -- value types, never a backend, extractor, or the cache -- performs zero filesystem mutation (`test_mutation_authority.py::PURE_MODULES`), and never raises.
- Decision: what crosses is `PerceivedEvidence` (`tools/ingest/naming/evidence.py`), a frozen dataclass of bounded strings and tuples only -- native/OCR/transcript excerpts capped at 1500 characters each and re-sanitized at the boundary, visual descriptions and entities, the first frame's image kind, headings, which kinds were actually *present* (not merely attempted), the warning codes, and the content hash. The perception layer's richer values (polygons, per-block confidences, provenance, page regions and tables) stop at the boundary on purpose: a proposer needs the words, not the geometry, and every extra field is one more thing a future consumer could mistake for authority. The sanitizer restates `evidence/types.py::sanitize_extracted_text`'s character classes rather than importing them (the guard forbids the import); a test compares the two functions directly over a payload matrix, so the duplication may exist but may not drift. `FileEvidence.transcript` is read with `getattr`, so the transcript workstream lands with no change here.
- Decision: `DeterministicProposer` gains two evidence-derived builders with honest confidence -- a document's first structural heading, or the first title-shaped line of its own text layer (0.70), and the title-shaped first line of OCR on a file already *proved* to be a screen capture by filename or configured folder (0.62). It reads **neither the transcript nor a visual description**: both are summaries something else wrote about the file rather than text the file contains, and `HeuristicVisionBackend` is explicitly a guess from colour distribution and flatness -- naming a video from one would assert certainty the evidence does not carry, the same reasoning that keeps `is_probably_screenshot` out of the generic fallback. Embedded `metadata_title` (0.92) still outranks a perceived heading, and where perception says nothing usable the generic factual fallback still beats invention.
- Decision: `SemanticProposer` (`tools/ingest/naming/semantic.py`) is opt-in via `naming.proposer: "semantic"` (default `deterministic`; `naming.enabled: false` still wins, so enabling a model is two deliberate settings) and is the first production caller of `tools/prompts/production.py::render_for_task_class` -- retiring D-051's "still never exercised by a production caller" and making D-041's shared-path claim real rather than aspirational. It is loopback-only by reusing, never reimplementing, `OllamaLocalClient.__init__`'s endpoint rule: a non-loopback endpoint becomes a *recorded fallback with a stated reason*, not a request, so no document text can leave the machine even if config says to send it. Its answer is unwrapped generously (markdown fences, quotes, a `Filename:` label, a trailing explanation; first line only, never scanned for a better candidate further down) and then judged strictly: a path separator or lookalike, `..`, a leading dot, a control/bidi/zero-width character, a changed or added extension, or a name over the policy length cap is **refused, not repaired** -- a name that had to be fixed is a name the model did not produce. Whatever survives still passes through `policy.validate_proposal` in `rename.py` exactly as a deterministic proposal does; the pre-check is defense in depth in front of that, never instead of it.
- Decision: confidence is derived deterministically, never self-reported. The model outputs only a filename, and a score it invented would be worth less than nothing given that a confidently wrong name is the failure mode this system exists to avoid. Base 0.70; minus 0.15 for an all-generic stem; minus 0.10 when no stem word appears anywhere in the evidence; plus 0.10 when two or more do; plus 0.05 for an owner-vocabulary word; clamped to 0.05-0.90. The ceiling sits below `CONFIDENCE_EMBEDDED_TITLE` (0.92) deliberately: a document stating its own title is stronger evidence than a model's reading of one, and a confidence able to exceed it would invert that. Any failure at all -- connection refused, timeout, `ValueError`, empty output, JSON, prose, a refused string, a derived confidence under `naming.semantic.min_confidence` -- falls back to the deterministic proposer (or declines when `fallback_to_deterministic` is false). A fallback keeps the semantic proposer's own `model_version` so `ledger.evaluated_by`'s "already answered" check still works and a fallback does not cost a model call on every later run, while `model` states plainly which code produced the string.
- Decision: `naming_history` gains six nullable columns in one additive migration on each database (local ledger 4, T7 catalog 5 -- the catalog needs them because `_attach_provenance` copies lineage rows across verbatim): `prompt_id`, `prompt_version`, `prompt_sha256`, `evidence_sha256`, `evidence_sources` (JSON array of kinds), `raw_output` (bounded). Nothing is backfilled -- a pre-migration row correctly reads `NULL`, because it was written by a proposer with no prompt and by a pipeline where naming could not see evidence at all. The raw output is recorded **even when the answer was refused**: a rejected hostile proposal that leaves no trace is indistinguishable from a rename nobody noticed. The evidence hash is read from the evidence the proposer was *handed*, not from the proposal, so a hostile proposer cannot write a different one into its own audit trail. `organize naming-history PATH` is a new read-only subcommand that prints it. Only the hash, the evidence kinds, the prompt identity and the model's one-line answer reach the T7 -- extracted document text stays in the un-backed-up Mac-side ledger, so D-030's privacy posture is unchanged.
- Decision (integration pass, 2026-09-18): an instruction is not a title. `tools/ingest/naming/quality.py::looks_like_instruction` is a bounded, one-line grammar check ("ignore … instructions", "AI ASSISTANT:", "rename this file", "your new task is", config-shaped `set key: value`) that the deterministic title scan skips past and the semantic proposer's output check refuses with a recorded reason. It is a naming-quality rule, not a prompt-injection defense -- the structural defense (perceived text can produce at most a policy-legal filename, never a path, extension change, config edit, or move) is unchanged -- but without it the first real acceptance drill named `scan_0001.pdf` `2026-09-18_ignore-all-previous-instructions.pdf`, which put attacker-shaped text on disk under the namer's byline. `tests/ingest/test_instruction_shaped_titles.py`.
- Consequence: the doc-level claim in `docs/17-file-evidence.md` changes from "evidence reaches no decision" to "evidence reaches only a name proposal that deterministic policy validates; retention and ingestion stay evidence-blind," and the tests and docstrings asserting the old wording were updated rather than left to rot -- including an explicit new test that a poorly-named pair of PDFs differing only in their text gets two *different* names and byte-identical retention. Prompt-injection text in a PDF or in OCR can now appear in a filename, and that is stated plainly in `docs/17` instead of being papered over: it is an ugly outcome, not an unsafe one, because it still cannot become a path, change the file type, relocate or overwrite anything, reopen a human-chosen name, or reach retention. No filtering for hostile phrasing was added; the defense stays structural.
- Revisit trigger: the semantic proposer's derived-confidence formula proves to be the wrong instrument -- either gating out good names or admitting hallucinated ones -- once it has run over a real corpus with a real model. Tune it from measured naming outcomes (the Naming Lab's raw-compliance-vs-end-to-end split is the right evidence) rather than intuition, and treat a *second* decision reading perceived evidence -- retention above all -- as a new decision entry needing its own review, not as an extension of this one.
## D-058 — Speech transcription is a third evidence seam; video evidence is fused with provenance
- Status: accepted 2026-09-17.
- Context: D-055/D-056 gave video sampled frames through the vision and OCR seams, and both entries left the audio half explicitly out of scope ("audio remains opaque (no speech-to-text ships)"). `router.py` still grouped `MEDIA_AUDIO` into `_OPAQUE_MEDIA_KINDS`, so a voice memo carried nothing but ffprobe container facts, and a video's spoken content — usually the single most informative thing about a walkthrough, a recorded call, or a screen capture with narration — was never perceived at all. D-056's own revisit trigger also named evenly-spaced-by-time sampling as a poor fit for a corpus with long static intros and outros.
- Decision: speech is its **own seam**, not an extension of OCR. `tools/ingest/evidence/backends/__init__.py` gains a fourth `Protocol`, `TranscriptionBackend` (`name`, `version`, `available()`, `transcribe(audio, *, timeout_seconds) -> TranscriptionResult`), alongside `TextExtractor`/`OCRBackend`/`VisionBackend`. A transcript has time structure, a language, and failure modes (hallucination over silence, a wrong language, a clipped tail) that look nothing like an OCR engine's, and a reader has to be able to tell "this file *says* invoice" from "this file *shows* the word invoice" — folding the two into one text field would destroy exactly that distinction. `FileEvidence.transcript: TranscriptEvidence | None` is a new field with a `None` default, so every existing construction and cached row keeps working; the attribute names `text`, `language` and `engine` on it are a deliberate public contract for a consumer reaching it through `getattr(file_evidence, "transcript", None)`.
- Decision: the seam is handed **bytes, never a path**. `AudioClip` (in-memory 16 kHz mono PCM WAV bytes, a duration, the source SHA-256, a measured peak amplitude) is to a speech backend exactly what `RasterImage` is to an OCR or vision backend, and for the same structural reason (D-029): a backend that may one day be a model server or someone else's plugin is not trusted and then constrained, it is simply not given the means to touch the filesystem. `AudioClip` and `TranscriptEvidence` were added to `tests/ingest/test_mutation_authority.py::EvidenceValueTypesCarryNoAuthorityTests._TYPES`, which asserts frozen-ness and the absence of any `Path`/`Callable`/`IO` annotation.
- Decision: **no temporary file, at either end.** `backends/ffmpeg_audio.py` (new; a third, then fourth, justified `subprocess` module in the register, alongside `tesseract.py`, `ffmpeg_video.py` and `transcription.py`) asks ffmpeg for `-f wav -ac 1 -ar 16000 pipe:1` — decoded audio on stdout, no `-y`, no output path — and `backends/transcription.py::WhisperCppBackend` feeds that WAV to `whisper-cli` on **stdin** (`-f -`) and reads JSON back on **stdout** (`-ojf -of -`). Both halves were verified on this machine before the modules were written (whisper.cpp 1.9.4 reads the placeholder-sized streaming WAV header ffmpeg writes to a pipe; and with `-f -` but no `--output-*` flag whisper-cli prints nothing at all, which is why `-ojf -of -` is load-bearing rather than decorative). `EvidenceLayerNeverWritesTests` therefore needed **no** justification mechanism and gained none: the evidence package still performs zero filesystem mutations. If a future whisper build stops accepting stdin, this backend must report itself unavailable rather than fall back to a `tempfile` — the same instruction `tesseract.py` already carries.
- Decision: **silence is an answer about the file, not an error and not a guess.** A speech engine run over silence does not return silence; it returns a confident hallucination. So `ffmpeg_audio` measures the clip's peak sample and refuses to produce a clip at all below `SILENCE_PEAK_THRESHOLD` (64 of 32767, roughly −54 dBFS), recording the new `no_audio` warning code — kept deliberately distinct from `backend_unavailable`, because one is a fact about the file and the other a fact about this machine. Neither is cached, for the same reason an unavailable backend is not (D-031): the answer cost nothing to reach and installing a decoder must re-ask.
- Decision: `router.py` removes `MEDIA_AUDIO` from `_OPAQUE_MEDIA_KINDS` and adds `r15-video-transcript` (`MEDIA_VIDEO` **with an audio stream** and transcription enabled), `r16-audio-transcript` (`MEDIA_AUDIO`), and `r17-transcription-disabled` (the config gate, mirroring `r10`/`r11`). Every pre-existing rule id keeps its exact meaning. `r15` checks `facts["audio_present"] is True` rather than truthiness: a probe that could not run leaves the fact absent, and spending an ffmpeg run plus a speech engine on "unknown" is precisely the blind expensive inference this pure router exists to prevent.
- Decision: frame selection becomes an explicit, documented, deterministic three-step algorithm in `backends/ffmpeg_video.py` — how many (`frame_count_for`), where (`_sample_timestamps`, unchanged), which survive (`deduplicate_frames`). `evidence.vision.video_frame_count`'s valid range tightens from 1–30 to **1–`MAX_VIDEO_FRAME_COUNT` (12)** because each frame is an ffmpeg run plus up to one vision call and one OCR pass; `frame_dedupe` (default true) collapses near-identical frames using an 8×8 average hash written in plain Pillow (no NumPy — a banned import here; no adapted third-party code) with a Hamming threshold of 4 of 64 bits, comparing each frame against every *kept* frame so an alternating two-shot clip keeps two representatives; and `frame_duration_aware` (default true) samples at most 2 frames under 4 s and exactly 1 under 1 s. A collapsed frame's representative **keeps its original 1-based sampling index**, so surviving `page` values may be non-contiguous — deliberately, because the index records when in the clip the frame came from. Dropped counts are reported as a new `deduplicated` warning, never silently absorbed. This addresses D-056's revisit trigger at the "same picture repeated" end; genuine scene-change detection remains out of scope.
- Decision: `tools/ingest/evidence/summary.py::perception_summary` is the one place that knows how to read a whole `FileEvidence` at once — frozen plain data, every text field hard-capped, every collection count-capped, and **every field attributed** to the producer that supplied it (`container_source`, `transcript_source`, `ocr_source`, a `source` per frame description). It imports nothing but `dataclasses` and this package's own `types`, so adopting it can never become the path by which perception reaches a decision, and it is listed in `PURE_MODULES`. Its one opinionated rule: **no single frame may dominate the OCR excerpt** — per-frame contributions are capped at 400 characters and a frame whose text repeats an earlier frame's is dropped, so a recurring lower-third caption collapses to one mention while two frames that genuinely differ both survive (`ocr_frames_seen`/`ocr_frames_used` report what that cost).
- Decision: **no machine path in code.** `evidence.transcription.model_path` names a model explicitly when an operator wants to; left unset, `transcription.resolve_model_path` consults the Angel whisper cache through `tools/models/storage.py` (`WHISPER_CACHE_DIR`, the variable `cache_environment()` already publishes, plus a new `whisper_model_in`/`whisper_model_from_environment` pair and a `WHISPER_MODEL_PREFERENCE` order). The default is therefore a *policy* — "the sanctioned, UUID-verified model cache" — and a machine that has not been through AI-storage preflight simply answers "no model", at which point the backend reports itself unavailable like any other absent engine. A cache key carries the model's file **name and size in bytes**, never its path: a key is published in the ledger and a directory layout is not evidence, and re-hashing a 148 MB model per file would cost more than the transcription it protects.
- Consequence: `evidence.transcription` ships **disabled**, with `backend: "null"`, exactly like `evidence.ocr` (D-032): `whisper.cpp` is an optional Homebrew binary and the ggml model is a ~148 MB artifact this repository neither ships nor downloads. CI needs no network, no model, no GPU and no large fixture; `tests/ingest/media_fixtures.py` synthesizes every video and audio fixture on the machine (ffmpeg `lavfi` sources, Pillow-drawn PNG sequences where frames must genuinely differ, macOS `say` for speech), and one real integration test runs the actual `whisper-cli` against the actual model when both are present. `organize evidence PATH` reports a transcript's **presence** — language, segment count, coverage, engine, model — and prints no transcript text unless `--show-text` is passed, because a transcript is a verbatim record of what was said in the owner's own recordings and D-030's rule for document text applies to it unchanged.
- Consequence: this changes nothing about authority. Naming, triage, retention and ingestion still import nothing from `evidence/`, the AST guard asserting that is untouched, and a video that *says* "delete everything" produces exactly one thing: a `TranscriptEvidence` containing those words. `tests/ingest/test_evidence_transcript.py` proves the transcript-shaped case at the evidence layer; `tests/ingest/test_evidence_security.py`'s stronger end-to-end claims are neither weakened nor replaced.
- Revisit trigger: (a) a real corpus shows the 8×8 average hash collapsing frames that a human would call different shots — the threshold and hash size are then a measured change, not a guess; (b) `max_audio_seconds: 600` proves too short for the recordings that actually matter, which is a cost/benefit call to make against observed files rather than in advance; (c) a second transcription backend (a Core ML or MLX whisper, a diarizing engine) is wanted — the seam is designed for it, but speaker labels are a schema change to `TranscriptSegment` and deserve their own review.

## D-059 — Reasoning models were never measured; the naming suite's five deferred defects are fixed as suite 1.1.0
- Status: accepted 2026-09-18 (`tools/models/ollama_local.py`, `tools/campaign/{manifest,execution,fingerprint,runner,store}.py`, `tools/bench/acb_v1/{semantic_naming,routing_classification}.py`, `tools/bench/{cross_validation,gate2_audit,gate2_failure_analysis}.py`, `docs/30-gate2-naming-audit.md`).
- Context: `gate2-validation-001` (2026-09-15, 660 records) produced Gate-2's first real numbers -- routing best 0.684 against a 0.80 threshold, naming best 0.214 against 0.75, and `gpt-oss:20b` 95-100 % `truncated`. A number is not a finding, so the whole chain that produced it was read link by link (`docs/30-gate2-naming-audit.md` section 1) before anything was concluded about the models. Three of the four headline numbers turned out to be measuring the harness.
- Decision: **a reasoning model's thinking is separated from its answer, and its output budget is declared.** Measured on this machine (Ollama 0.33.3, `gpt-oss:20b`, MXFP4): `think: false` is accepted and silently ignored -- the model reasons anyway -- and its reasoning shares the single `num_predict` budget with its answer. At 64 the reasoning alone spent all 64 tokens (`done_reason: "length"`, `response: ""`); at 512 the identical prompt answered correctly in 76. So `OllamaTextProvider` now passes `think` through verbatim, including Ollama's `"low"`/`"medium"`/`"high"` effort levels, and returns `thinking` separately from `output` -- only `output` is ever scored; a candidate may declare `reasoning: true`, which is part of its configuration fingerprint and makes `tools/campaign/manifest.py` **refuse** any `num_predict` below the measured floor of 512, so the defect cannot be re-run by accident; `num_predict` is per-candidate; `truncated` stays a first-class status and now outranks whatever the verifier would otherwise have complained about for a half-written answer; and `thinking_chars` plus the attempt's own `num_predict` are recorded (result-record schema v3). `tests/test_reasoning_models.py` pins all of it against a fake provider, with no model or network involved. Re-measured on the dev split, `gpt-oss:20b` went from unmeasurable to 0.579 routing / 0.857 naming with the *same* prompt 1.0.0 it had scored 0.00-1.00-on-5-samples with before.
- Decision: **the five semantic-naming defects D-054 recorded as known and deliberately deferred are fixed, as a versioned suite bump to `1.1.0`** (`SUITE_VERSION`), with the change log in the module docstring beside the code and a written reason per item (`docs/30-gate2-naming-audit.md` section 3): (1) `allowed_dates` and `require_date` are **derived** from the ISO dates visible in the item's own `evidence_text` rather than hand-maintained, because five of fourteen validation items showed the model a date and then rejected it for using that date -- deriving them makes the drift unrepresentable rather than fixed once; (2) the prompt's "optional leading ISO date" wording is replaced by the rule the oracle enforces, and the mismatch check stays live so an old prompt paired with this suite is still reported; (3) a date is detected anywhere in the proposed stem (`YYYY-MM-DD`, `YYYY_MM_DD`, compact `YYYYMMDD`, each calendar-validated) instead of only as a prefix, because an anti-hallucination check that is evaded by moving the date one character right is not a check; (4) concept matching is stem-, word-family- and phrase-aware instead of single-token exact equality, because a "synonym set" compared by `==` is exact-string matching with extra steps -- forbidden tokens deliberately keep exact matching, since widening a prohibition fails correct names; (5) extension exactness is evaluated alongside every other check and reported separately (`checks`, `failures`, `raw_compliance`, `semantic_pass`), because 1.0 returned on the first extension mismatch and therefore recorded all 70 of `gpt-oss:20b`'s empty naming answers as `wrong_extension`, which is actively misleading about what happened. An empty answer is now `empty_output`.
- Decision: two further items are corrected for the same class of reason, and one is refused. The `ambiguous_asset` scenario demanded one specific generic noun (`photo`/`photograph`/`image`) for evidence that deliberately identifies nothing, so `blurred-outdoor-scene.jpg` -- a better filename than `photograph.jpg` -- failed; those items are now scored on evidence groundedness (at least two content words from their own evidence text, computed mechanically, so the rule is identical in all three splits and nobody read holdout content to write it). `sn-injection-val-01` forbade the token `system` while requiring the entity *Cobalt Systems*; the prohibition is removed and an audit check now refuses any item that both requires and forbids a token. Refused: `rc-prompt_injection-val-02`, where both `qwen3.5` candidates answered `routing` instead of `classification` -- the item is sound and the real gap was that the prompt published fifteen label names and defined none, which is a prompt defect (fixed in prompt 1.1.0), not a benchmark defect.
- Decision: the routing suite is reviewed for the same defect class and also bumped to `1.1.0`. Format compliance is reported separately from classification correctness (`format_clean`, `unwrapped`, `label_correct`): passing still requires exactly one bare label, because a caller that has to parse prose has not got a classifier, but `label_not_in_closed_set` counts are no longer uninterpretable. One ground-truth label is corrected: `rc-model_assisted_work-val-01` ("turn this rough bullet list from a meeting into a coherent short summary paragraph") was `repo.documentation`, whose production definition is "Summarise or document a repository", while the same scenario's dev item was `general` -- the suite asked for two different answers to the same question in two splits. It is now `general`.
- Decision: the D-043 independent second oracle (`tools/bench/cross_validation.py`) is updated in step and re-proven to agree -- date-anywhere scanning, word-family matching and the evidence-grounding rule reimplemented from scratch there, sharing no code with `tools/bench/acb_v1/*`, with agreement asserted across twenty representative and adversarial naming cases and six routing cases (`tests/test_acb_v1_suite_v110.py::CrossValidationAgreementTests`). An oracle fix that silently left the cross-check behind would have removed the only evidence that Angel's oracle is not grading itself incorrectly.
- Decision: the contamination guard is enforced where it matters instead of only in tests. `assert_no_holdout_leak` was written as a run-time guard (D-052) but was only ever exercised against whichever prompt version happened to be `active`; a campaign may pin any version, including a draft carrying few-shot examples. `tools.campaign.runner.check_prompt_contamination` now runs it over the exact prompt versions a campaign will send, on both `dry-run` and a real run, **before** any model is staged or loaded. The runner additionally refuses to keep two candidates that share one Ollama model tag resident at once -- a prompt-variant experiment has several candidates over one model, and each batch unloads that tag when it finishes, which would have evicted a concurrent sibling's weights mid-batch.
- Decision: `tools/bench/gate2_audit.py` becomes the standing regression guard for all of it (audit schema v2). It runs, deterministically and against the live objects: answer-leakage and few-shot-contamination checks in both directions; the real holdout guard, with its verdict recorded as a finding; live oracle probes that assert an answer assembled only from an item's own expectations passes (false negative) and that the unchanged original name and a contentless `document.ext` both fail (false positive); extension-separation; concept-set evidence groundedness; required-vs-forbidden contradictions; leakage-check groundedness; uncertainty guidance; and scenario/label balance. `./scripts/angel-eval audit --strict` exits non-zero on any error-severity finding; it now exits zero. `tools/bench/gate2_failure_analysis.py` gains per-scenario breakdowns and an `attribution_hint` per failure category, explicitly labelled a triage hint rather than a verdict: only `verifier` and `infrastructure` are recorded facts, while `model` versus `prompt_contract` is an inference to be checked against the raw output.
- Consequence: three findings are reported and deliberately **not** fixed, because fixing them would change what the suite measures rather than repair a defect: both suites carry one or two items per scenario per split, so a split-level pass rate weights the two-item scenarios double; `general` is the correct routing answer for 12 of 57 items, so a model that always answers `general` scores 21 % without classifying anything (which is close to what `qwen2.5:0.5b` did in `gate2-validation-001`); and `routing` is published on every item while being the correct answer for none.
- Consequence: suite versions are part of every configuration fingerprint, so 1.1.0 results are mechanically a different set of work units from 1.0 results. `gate2-validation-001`'s 660 records are untouched and are still the measurement of the 1.0 configuration; they are not reinterpreted as evidence about 1.1.0, and `gate2-validation-002` is a new campaign id rather than a resume. One consequence of adding `reasoning` to the candidate identity is that `config/campaigns/gate2.yaml`'s manifest fingerprint moved, so `gate2-validation-001` can no longer be resumed under its own id -- correct, since its configuration no longer exists, and it was never going to be resumed.
- Revisit trigger: a runtime appears whose reasoning channel is *not* separable from its answer (no `thinking` field), at which point "only the answer is scored" needs a different mechanism than reading a second field; or a future suite version wants to change what an item expects, at which point this entry's rule applies -- a versioned bump with a written reason per item, never an in-place edit.

D-051 had already made the dependency explicit -- an unpinned prompt version cannot satisfy any certification -- and `config/certifications.example.yaml` had been the empty list since D-051 precisely because nothing had been measured.

Without that arm the prompt's contribution would have had to be inferred from the dev split. It is also the clearest possible evidence for why a certification pins `prompt_version`: on these numbers the same weights are a qualifying configuration or a failing one depending only on which prompt version they are asked with.

Measured envelope: p95 latency 1.74 s (routing) / 2.36 s (naming); resident footprint 5,498,564,770 bytes read from Ollama `/api/ps` under this exact configuration rather than estimated.

The file is gitignored and machine-specific -- a certification names the exact local model digest measured on one host (`6488c96f...`) -- so `config/certifications.example.yaml` stays the committed empty list `tests/test_autonomous_routing.py` asserts, and `tests/test_certification_file.py` validates the real file wherever one exists (thresholds met, prompt version resolvable, suite version current, envelope present, failure modes recorded) and skips where none does.
- Decision: the task class `routing` is deliberately **not** certified, even though `tools/models/task_classes.py` gates it with the same suite and the loader would have accepted the record. That suite measures classifying work into the taxonomy; it never asks a model to emit a routing decision, and the label `routing` is in fact the correct answer for none of its 57 items. Certifying it would be an overclaim of exactly the kind D-044 exists to prevent.
- Consequence: the certification is real but currently **inert**, and honestly so. `model:` is the registry entry name the router looks a candidate up by (`tools/router/router.py::_certification_gate` passes `spec.name`), and this machine has only `config/models.example.yaml`, where `capable-local` is `model_id: REPLACE-after-measurement` with `enabled: false`. Filling in a real `config/models.yaml` is a separate, deliberate act; certifying a configuration and wiring a registry entry to it are two different decisions, and conflating them is how a measurement silently becomes permission. Nothing in this entry grants any model authority to rename a file: D-022's proposal-only boundary is untouched.
- Consequence: what still fails at the certified configuration, with the locus the analysis assigns it. Routing (holdout), 2 of 19 items, both `model`: one labels a physically impossible request `escalation_required` instead of `unsupported`; one answers with the modality of the attached material instead of the job's own task class. Both 5 of 5 samples -- consistent, not noise. Naming (validation), 1 of 14 items: on the deliberately unidentifiable asset it returns the original filename unchanged, which the production quality gate rejects as not an improvement. Whether declining to rename an unidentifiable file is the *better* production behaviour is an open question this suite currently answers "no"; if production prefers the decline, the suite is wrong there and that is a benchmark-design decision for a later pass with its own version bump, never an adjustment to make a number look better.
- Consequence: **fine-tuning is not justified by this evidence.** The best configuration is above both thresholds on a blind split with no prompt or oracle changes left to make, and the remaining failures are three specific taxonomy-boundary cases, not a broad capability deficit -- two of them arguably ambiguous items and one arguably a benchmark-design question. The measured ordering of what mattered was: harness defects first (naming 0.214 -> 0.714 with the prompt unchanged), prompt second (routing 0.632 -> 1.000 on identical weights), model third. Fine-tuning would be the fourth-largest lever, on 33 validation/holdout items, against a model that already answers 0.895-1.000. The honest next steps are more items (both splits are 19 and 14, so intervals are wide), a second capability's suite, or a production caller -- not a training run. Revisit only if a materially larger corpus shows a failure *class* rather than three cases, and only then against a measured baseline this pass now provides.
- Revisit trigger: the certification expires 2027-03-18, or sooner if the model tag's digest changes, the runtime is upgraded, the prompt version moves, or a suite version bumps -- each of those is a configuration mismatch the router already refuses rather than silently tolerates. Also revisit if `config/models.yaml` is created, at which point this certification stops being inert and its first real routing decisions should be reviewed against the ledger.

- Status: accepted 2026-09-17 (`templates/app-spec/schema-v1.json`, `tools/appspec/`, `templates/app-spec/examples/`, `docs/28-application-spec.md`, `tests/test_appspec.py`).

- Decision: four representative, realistic-but-fictional example specs (`squad-quit.yaml`, `nurse-shift.yaml`, `single-player-game.yaml`, `multiplayer-game.yaml`), one per known backend-profile class, each validating cleanly including every semantic check.

## D-063 — V1 adversarial review findings
- Status: accepted 2026-09-18 (`tools/ingest/naming/policy.py`, `tools/ingest/naming/quality.py`, `tools/ingest/config.py`, `tools/ingest/cli.py`, `tools/angel_sync.py`, `tools/fixtures/spec.py`, `scripts/bootstrap-t7.sh`, `docs/08-security-threat-model.md`, `tests/ingest/test_adversarial_v1.py`).
- Context: an adversarial pass over the V1 completion surface, taken on the premise that the existing mutation-authority, evidence-security and transaction tests all pass and the interesting failures are therefore the ones nobody wrote down. Seven were real. Four of them moved a boundary this repository documents, which is why they get a decision entry rather than only a commit message. Nothing here relaxes an existing guard: every fix is additive, the suite went 1290 -> 1320 tests with no change to an existing assertion, and the one fix that *would* have weakened an existing test (sanitizing `raw_output` where it is stored, which `tests/ingest/test_semantic_proposer.py` asserts is verbatim) was moved to the print boundary instead.
- Decision: **the filename sanitizer filters by Unicode category, not by a hand-written list.** `sanitize_stem` named two sets of characters explicitly -- C0 controls, and nine of the zero-width/bidi-override characters -- and its docstring plus `docs/16` claimed it removed "control characters and zero-width/bidi-override characters". It did not. C1 controls (U+0080-U+009F), U+200E/U+200F (the bidi *marks*), U+202C, U+00AD, U+2060-U+2064, U+061C, U+180E, every private-use character and every lone surrogate reached an applied filename. U+009B is CSI -- the single byte that starts an 8-bit ANSI escape sequence in a terminal that honours one -- and `organize` prints filenames to a terminal, so the most durable place in the system to park a terminal payload was a filename. `evidence/types.py` already strips C1 from extracted *text* for exactly this reason; the naming side had never been given the same treatment. The filter is now `unicodedata.category(character) not in {"Cc", "Cf", "Cs", "Co"}`, with the hand-written sets kept as documentation of intent and now a strict subset of it. A hand-enumerated attack class is a list of the members somebody thought of.
- Decision: **a lone surrogate is a recorded policy rejection, not an encoding crash.** A surrogate reached `len(filename.encode("utf-8"))` and raised `UnicodeEncodeError`, which is not a `NamePolicyError`, so `rename.py` did not catch it: the per-file handler in `pipeline.py` recorded a bare error string and **no `naming_history` row**. That is precisely the outcome D-057 says the audit trail must never have -- "a rejected hostile proposal that leaves no trace is indistinguishable from a rename nobody noticed". The categorical filter removes surrogates before the length check, so the branch is unreachable and the length check remains only as a backstop.
- Decision: **the 255-byte component ceiling is a limit to trim to, not a reason to refuse.** `max_length` counted characters; APFS counts bytes, and the two diverge 3x for CJK and 4x for emoji. So a name that cleared the configured readability cap overflowed the hard ceiling and `validate_proposal` refused it outright -- meaning no document with a full-length Japanese, Chinese, Russian or Greek title could ever be named. `sanitize_stem` now takes `max_bytes` (default `MAX_COMPONENT_BYTES`), truncates on a character boundary rather than inside a multi-byte sequence, and `validate_proposal` passes a budget leaving room for the extension and for the `file-` prefix a reserved stem can acquire. `docs/16`'s "readability cap ... hard ceiling underneath it" is now true.
- Decision: **filename quality is Unicode-aware, and this is a mutation-authority fix rather than an i18n nicety.** `quality.tokenize` split on `[^A-Za-z0-9]+`, which treats every non-ASCII letter as a *separator*: `отчет-о-финансовых-результатах.pdf` produced zero tokens, `確定申告書.pdf` produced zero, and `café-menu` produced `caf`. Zero meaningful tokens means POOR, and POOR means **eligible for automatic renaming** -- so invariant 7 ("a useful name is left alone") silently did not hold for any name the owner wrote outside the Latin alphabet, while `validate_proposal`'s quality re-check simultaneously refused every replacement in the same script. Such a file was both permanently eligible and permanently unnameable. `_SPLIT_RE` is now `[\W_]+`, which is character-for-character equivalent on ASCII input (proved by the whole existing suite staying green, plus an explicit ASCII-invariance test), and a two-character token counts as a word when it is East Asian wide or fullwidth, because 報告 is a word in two characters where `ab` is not.
- Decision: **a caller-supplied string may not become a path component under the verified volume root.** `angel-sync archive --name` passed straight into `mirrors_dir / f"{name}.git"`. With a name like `sub/../../../../tmp/evil`, the mirror clone created the bare repository *outside* the resolved root (the clone creates leading directories), and the `staging.rename(mirror)` that followed raised an uncaught `FileNotFoundError` out of `main()` -- so the one invariant `angel_sync` exists to hold was decided by a command-line argument. `validate_mirror_name` is now an allowlist (`^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$`, no `.`/`..`/`.git`, no trailing dot) applied in `refresh_mirror`, the single point both the mirror and archive paths pass through, and again in `cmd_archive` before the volume is even resolved. A denylist of `..` and `/` would still have admitted a leading dot (a mirror no listing shows) and a trailing dot (which some filesystems strip, so the path written and the path reported differ). Two adjacent holes closed with it: a **symlink** at the mirror path is refused rather than fetched through, and a **non-git directory** there is refused with that as the stated reason rather than with whatever error the fetch happened to produce.
- Decision: **`t7.inbox_relative_path` and `t7.system_relative_path` are validated relative and `..`-free.** Both are joined to the UUID-verified root by `resolve_t7`, and `Path(root) / "/tmp/x"` in pathlib *is* `/tmp/x` -- so an absolute value silently relocated the catalog, the staging directory, the sidecars and the whole organized inbox off the verified volume, and a `..` value walked out of it. `automation.state_relative_path` has been validated for exactly this since it was added; these two were the gap, and D-026's rule is that a config file alone must never be able to move a write target outside the volume the UUID check resolved.
- Decision: **`load_fixture` validates `task_id` like every other name in a manifest.** `starter_files` and `probes` were each checked against `..` and an absolute path; `task_id` was not, and `fixture_dir = root / task_id` is where `probes.load_probe_builder` finds the `probes.py` it hands to `exec_module`. `task_id` arrives from a corpus JSON whose path is a caller argument (`load_corpus(path)`), so this was the one code path in `tools/` able to execute Python from outside the reviewed tree -- including from a mirror or from `40-ai/skills/candidates/`, which docs/26 says is never executed. The test plants a *structurally valid* bundle whose `probes.py` writes a marker file on import, so "was it executed?" is a fact on disk rather than an inference from an exception type.
- Decision: **the terminal is an output boundary, and `_print_excerpt` is safe regardless of its caller.** Its docstring justified printing raw on the grounds that every caller had already sanitized. One had not: `raw_output` is bounded to 500 characters and stored **verbatim**, which is deliberate -- a zero-width character or a NUL is *why* an answer was refused, and a column that had quietly removed it would show a legal-looking name beside a rejection reason that made no sense. So the strip moved to the print boundary, which is where attacker-influenced text actually meets a terminal, and which also protects every row written before anyone considered this. The stored column and its verbatim assertion are unchanged.
- Decision: **`scripts/bootstrap-t7.sh` resolves its root before deciding whether it is a volume.** The "a root under `/Volumes` requires `--expect-uuid`" gate was a string prefix test on the argument, so `/tmp/angel` symlinked to the real volume, or `../../Volumes/Angel`, both named it and both skipped UUID verification entirely -- on precisely the disk the gate exists to protect. `ROOT` is now normalized through `cd "$ROOT" && pwd -P` first.
- Consequence: `docs/08-security-threat-model.md` gains a "V1 adversarial review — 2026-09-18" section listing what was probed, what held, what was fixed, and three findings **accepted rather than fixed** with the reason: a volume physically swapped for a different one at the same mount path mid-run (re-verifying the UUID per file would cost a `diskutil` call per file; a destination that merely vanishes costs the transfer and never the source, which is tested), the verbatim `raw_output` column above, and pypdf's own parse diagnostics on stderr during a scan.
- Consequence: `tests/ingest/test_adversarial_v1.py` is 35 cases in six groups, and every regression case in it was verified to **fail** against the pre-fix sources -- 69 failures and 12 errors when the fixes are reverted with the tests left in place -- so none of them is a test that only asserts its own fixture. The fuzz case (~2500 byte mutations of synthesized mp4/m4a/pdf/xlsx fixtures, zero escapes from `collect_evidence`) is seeded and wall-clock-bounded, and asserts it produced enough cases to mean anything rather than passing vacuously on a slow machine.
- Revisit trigger: (a) a non-Latin filename corpus shows the two-character East-Asian-width rule admitting tokens a reader would call meaningless, at which point it is tuned from observed names rather than from this reasoning; (b) a second caller-supplied string becomes a path component under the volume root, at which point `validate_mirror_name`'s shape is the thing to reuse rather than a second bespoke check; (c) perceived evidence is ever proposed as an input to retention, at which point every finding here about *naming* has to be re-asked about a decision with a much larger failure size.
